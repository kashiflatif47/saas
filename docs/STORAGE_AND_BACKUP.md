# Permanent image storage, backup and recovery

Restaurant **data** (settings, branding, menus, orders, staff, customers…) lives in **MongoDB**.
Restaurant **images** (logo, favicon, banners, category and dish photos) live in **permanent object storage**:
Cloudinary or an S3-compatible bucket (AWS S3, Cloudflare R2, Backblaze B2, MinIO…). Neither depends on the app
folder, so builds, GitHub pushes, Hostinger redeployments and restarts cannot delete them.

> Why this exists: uploads used to be written to `UPLOAD_DIR=uploads` *inside* the deployed app. A redeploy
> replaced that folder and the files were gone while MongoDB still pointed at them (`/uploads/...` → 404).

## How it works

| Piece | What it does |
|---|---|
| `Asset` collection | One document per image: restaurant, provider (`cloudinary`, `s3`, `external`, `local`), provider key/public ID, bucket, delivery URL, MIME type, size, SHA-256 checksum, timestamps, previous locations (`history`), last integrity check. |
| `/media/<assetId>` | The **stable address** saved in branding, categories and dishes. It redirects to the image's current location (signed link for private buckets). Moving an image to another provider changes the Asset, never the address. |
| `services/media.ts` | The single storage service: `uploadAsset`, `createExternalAsset`, `importExternalAsset`, `getAssetUrl`, `deleteAsset`, `copyAsset`/`migrateAsset`, `migrateLegacyUpload`, `inspectAsset`, `verifyAsset`. Every upload route uses it. |
| Old `/uploads/...` | Still served exactly as before, so nothing breaks before migration. The application no longer deletes these files. |

Three ways to add an image (one control everywhere in the admin):

1. **Upload to Cloudinary**: the file goes through the server to Cloudinary's signed upload API.
2. **Upload to Cloud Storage**: the file goes through the server to the S3-compatible bucket (AWS Signature V4).
3. **Use an existing image URL**: https only. The server validates the link but does **not** fetch it; the browser
   shows a live preview. The image depends on its original host. **Copy to Cloudinary / cloud storage** makes a
   permanent copy using an SSRF-protected download (public https host on port 443 only, private networks refused,
   no redirects, size and time limits, real-image check).

### Upload guarantees

- The file type is checked from its bytes (PNG, JPEG, WEBP, ICO) and the size is limited (`MAX_UPLOAD_MB`).
- Object keys are generated by the server (`tenants/<restaurantId>/<purpose>/<random>`); file names are never used.
- The upload is **verified** (exists, size, checksum) **before** any record changes. If the provider fails, the
  admin sees the error, no Asset is saved, and the current image stays.
- **Replacing** an image retires the old Asset (`status: replaced`); its bytes are kept and it can be attached again.
- **Removing** is soft (bytes kept). **Permanent deletion** is limited: owner only, typed confirmation, never while a
  record still uses the image, never for an active image. Earlier copies in `history` are never touched.
- Production never stores uploads in the app folder. With no cloud provider configured, uploads are refused with a
  clear message. A local folder is accepted only if `UPLOAD_DIR` is an absolute path outside the app **and**
  `LOCAL_UPLOADS_PERSISTENT=true` confirms the host keeps it across releases.
- Credentials stay on the server: environment variables, or the platform console (encrypted with
  `ENCRYPTION_KEY`). They are never returned by any API or written to logs.

## Setting up a provider (no purchase needed to start)

Both Cloudinary and Cloudflare R2 have free tiers. **Creating accounts and any paid plan is the owner's decision.**

**Cloudinary**: Dashboard → API keys: copy the cloud name, API key and API secret. Enter them in Platform console →
**Storage** → Cloudinary → Save → **Test connection**, or set `CLOUDINARY_CLOUD_NAME`, `CLOUDINARY_API_KEY` and
`CLOUDINARY_API_SECRET` in the server environment.

**Cloudflare R2** (S3-compatible):
1. Create a bucket.
2. R2 → Manage API tokens → *Object Read & Write* for that bucket.
3. Use these settings:
   - endpoint: `https://<account-id>.r2.cloudflarestorage.com`
   - region: `auto`
   - path-style: on
4. Optional: connect a custom domain or `r2.dev` URL as the **public base URL**. Without it, keep the bucket
   private and images are served through 10-minute signed links.

**AWS S3**:
- endpoint: `https://s3.<region>.amazonaws.com`
- region: e.g. `eu-central-1`
- Use an IAM user limited to this bucket.

**Backblaze B2**:
- endpoint: `https://s3.<region>.backblazeb2.com`
- region: the part shown in the endpoint, e.g. `us-west-004`
- path-style: on

## Protecting images from deletion

Cloud storage on its own does not prevent deletion. Configure these at the provider:

- **Object versioning**: on (S3 and B2 support it; R2 supports bucket lock / retention rules). An overwritten or
  deleted object can then be restored.
- **Least-privilege keys**: the app needs PUT, GET and HEAD. Leave out **DELETE** unless you want the owner's
  "Delete permanently" action to work; without it, that action fails safely and nothing is lost.
- **No lifecycle / expiry rules** on the images bucket or prefix.
- **Cloudinary**: enable *Backups* (Settings → Upload → Backup) where your plan allows it. Restrict who has
  dashboard access.
- The app itself never deletes source copies when replacing, importing or migrating images, and a daily job
  (`assets.verify`) checks that every stored image is still present with the same checksum. Failures appear in the
  owner's Menu/Branding pages as "missing images".

## Moving existing images to permanent storage

```bash
# 1. Report only (nothing changes): what would move, and which originals are already missing
npm --prefix server run assets:migrate -- --to cloudinary --dry-run

# 2. Migrate; keep the report
npm --prefix server run assets:migrate -- --to cloudinary --report migration-report.json
#    production build:  npm --prefix server run assets:migrate:prod -- --to cloudinary

# 3. Switching providers later (images already in permanent storage keep their /media address)
npm --prefix server run assets:migrate -- --to s3 --assets
```

For every image, the migration:
1. Reads the original.
2. Uploads it and confirms the object exists.
3. **Downloads the copy back and compares SHA-256 checksums.**
4. Only then changes the record, and only if the record still points at the old file.

The original file is **never deleted**. Missing originals are reported as `missing`; restore them from a backup
(see below) and run the migration again, or re-upload the image in the admin. Nothing is substituted.

## Backups (both halves)

A MongoDB backup alone is not enough: it contains *references* to images, not the images.

**1. MongoDB (data + image references)**
- MongoDB Atlas: enable **Cloud Backup** (continuous / point-in-time where the tier allows), or schedule
  `mongodump --uri "$MONGODB_URI" --archive=tablesaas-$(date +%F).gz --gzip` daily and keep copies off the server.
- The `assets` collection is essential: it maps `/media/<id>` to the stored objects.

**2. Images**
- **S3 / R2 / B2**: versioning (above), plus optionally a nightly copy to a second bucket or account
  (`rclone sync r2:menu-images b2:menu-images-backup`, or provider replication).
- **Cloudinary**: Cloudinary backups (plan-dependent), and/or a periodic export with the Admin API / `cld` CLI to an
  S3 bucket.
- **Legacy `/uploads` folder** (until migrated): copy it off the server now; it disappears on the next redeploy.

## Restore procedure

1. **Restore images first** to their original keys. Use the bucket version history, the backup bucket, or the
   Cloudinary backup. Keys are recorded in each Asset (`provider`, `bucket`, `key`), so `mongosh` can list exactly
   which objects are needed:
   `db.assets.find({ status: { $ne: "removed" } }, { provider: 1, bucket: 1, key: 1 })`
2. **Restore MongoDB** from the same point in time (`mongorestore --archive=... --gzip`, or Atlas restore). Restore
   into a new database first and switch `MONGODB_URI` only after checking it.
3. **Verify**: open the owner's Branding and Menu pages (the "missing images" panel lists anything still absent), or
   call `POST /api/staff/assets/<id>/verify` per image.
4. For legacy `/uploads` references, put the files back under `UPLOAD_DIR/<restaurantId>/...`, then run
   `assets:migrate` so they stop depending on the server folder.

## Hostinger notes

- Keep the existing Node.js app; no hosting change is needed. Add the provider variables in hPanel → the app's
  environment variables (or use the platform console), then redeploy once.
- Do **not** set `LOCAL_UPLOADS_PERSISTENT=true` unless you have confirmed, with Hostinger, a folder outside the app
  that survives redeploys. The default is to require Cloudinary or S3-compatible storage in production.
- Deployments never run the seed script; `bootstrap` only creates missing defaults and never overwrites data.
